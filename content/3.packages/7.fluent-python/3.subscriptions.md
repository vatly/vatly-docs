Authorize a `LocalSubscription` from your repository, then call
`vatly.subscription(local)`. `swap(plan_id, body)` defaults to scheduled changes;
`swap_and_invoice` forces immediate application/invoicing; `swap_without_charge`
forces immediate application and disables the proration charge. Local data follows
the API response, so a scheduled swap does not prematurely replace the active plan.

`cancel(immediately=True)` sends the API mutation and waits for signed events to
update local cancellation state. `resume()` clears local `ends_at` after API success.
`sync()` saves the complete snapshot and derives expiry through `subscription_ends_at`.
Grace expiry uses the next renewal, renewed-until or trial end (in that order),
excluding historical dates at/before cancellation, then a previously known valid
expiry. Conflicting usable trial and cycle deadlines raise `FluentError` rather
than guessing whether the subscription was on trial; the API omits that flag.
Equal instants are not conflicting, even with different timezone offsets.
`canceled_at` is the request time, never a grace deadline. If no deadline
is available, processing also raises `FluentError` and rolls back; monitor failures and
reconcile instead of assuming a new expiry. The prior committed state remains
until recovery, so hosts must apply their own stale-state entitlement policy.
Terminal cancellation uses `ended_at` or `canceled_at`; an active snapshot clears
stale expiry after a missed resume. Webhooks and Django reconciliation use the same
mapping. Core's internal `ends_at` is not currently exposed; `next_renewal_at` alone
must not be assumed universally present after cancellation.
`scheduled_update`, `has_scheduled_update`, and `cancellation_reason` read remotely.
`update_billing(body)` returns a hosted URL; both redirect defaults/overrides are required.

`model()` is local. `state()`/`subscription_state(ends_at, now)` implements PHP's
endsAt predicates: active/valid through grace period, recurring before cancellation,
ended at or beyond the end time. **Check Vatly status separately before granting
access**; these convenience predicates do not account for paused/unpaid states.

## Initial subscription linking

This alpha's linkage code reports `subscription_plan` lines as `legacy_plan_ids`.
It does not consume a related-resources subscription reference. Do not assume
an API addition alone completes this integration; package support must be
implemented and tested separately.

For existing subscription-valued lines, `await vatly.reconcile_checkout(checkout_id)` follows
host records → checkout → order → distinct subscription IDs, retries each 404 up
to three times (configurable 1–10), and returns `CheckoutResolution` with resolved
resources, `pending_subscription_ids`, and legacy IDs. Two lines for the same plan
can identify different subscriptions; quantity never multiplies IDs.

An unresolved subscription ID is not evidence of entitlement. Enqueue bounded
recovery and inspect ownership/status before granting access. The caller authorizes
the checkout and wraps local writes in its driver transaction. Built-in reactions
make no API reads. A future related-resources integration must preserve confirmed
IDs across older null snapshots and refresh unresolved signup correlation via GET;
core does not promise historical inference or backfill. Trial AUTH_REQUEST flows
may have no merchant order.paid event; explicitly reconcile the paid checkout's orderId.
