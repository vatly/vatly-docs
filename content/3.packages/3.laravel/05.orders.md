Orders represent completed transactions in Vatly. They are created automatically when a checkout completes or a subscription renews.

## Listing orders

```php
// Get all orders for a user
$orders = $user->orders;

// Orders are sorted by most recent first
$latestOrder = $user->orders->first();
```

## Why an order was canceled

Vatly tags an order with a reason when payment recovery for the unpaid order is exhausted. On the `order.canceled` webhook the package stores it in the `cancellation_reason` column on the `vatly_orders` row:

```php
$order->status;              // "canceled"
$order->cancellation_reason; // "payment_failure", or null for any other order
```

The same value is on the dispatched `Vatly\API\Webhooks\Events\OrderCanceled` event as `$event->cancellationReason`. Compare it against `Vatly\API\Types\CancellationReason::PAYMENT_FAILURE`.

Existing installations need the new column. Publish the migrations again with `php artisan vendor:publish --tag=vatly-migrations`, keep the new `add_cancellation_reason_to_vatly_orders_table` migration, delete the other newly published copies, and run `php artisan migrate`.

## A subscription's order lines

Each line stored from an `order.paid` webhook records the subscription it belongs to in the `subscription_id` column on `vatly_order_lines`, including the initial signup line, which references the plan (`product_type` is `subscription_plan`). List every line of a subscription, initial order included, through the order-line repository:

```php
use Vatly\Fluent\Contracts\OrderLineRepositoryInterface;

$lines = app(OrderLineRepositoryInterface::class)->listForSubscription($subscription->vatly_id);
$orderIds = array_unique(array_map(fn ($line) => $line->getOrderId(), $lines));
```

`subscription_id` is null on one-off lines, on lines Vatly created before it carried the link, and on a signup line whose subscription was not yet available when the order was paid. Lines are written once, so such a line stays unlinked. `listForSubscription()` also returns renewal lines whose `product_type` is `subscription` and `product_id` is the subscription id, so renewals stored without the link still appear.

Existing installations need the new column. Publish the migrations again with `php artisan vendor:publish --tag=vatly-migrations`, keep the new `add_subscription_id_to_vatly_order_lines_table` migration, delete the other newly published copies, and run `php artisan migrate`.

## How it works

Orders are synced from Vatly via webhooks. The `orders()` relationship returns all orders associated with the billable model through a polymorphic relationship.
