title: "Webhooks, storage and outbox"
description: "Vatly Django - Webhooks, storage and outbox"
---

Register the configured HTTPS `billing/webhook/` path in Vatly separately. Setup
and CI never register endpoints or create remote test data. The route verifies raw
request bytes against Vatly-Signature (SDK HMAC, default ±300 seconds, secret rotation).
The signed event.id is the dedup key; untrusted event-ID headers are ignored.
Invalid signatures/payloads are 400, wrong methods405, committed duplicates200.
Processing failures propagate as 500 so Vatly retries; all local writes roll back.

Each scope+mode has a BillingScope row. An atomic UPDATE acquires its write lock
before dedup reads, serializing callbacks across workers. The same transaction
contains WebhookCall audit, immutable Checkout/ResourceLink writes, complete
BillingResource snapshots, processed_at and Outbox rows. PostgreSQL is recommended
for concurrent production workers. SQLite supports local development; lock contention
may fail a delivery, which is safe to retry. Database uniqueness is the final guard.

Fluent's async protocols use thread-sensitive sync_to_async. ORMDriver.process
bridges the work callback with async_to_sync while the outer atomic transaction is
open, so nested writes remain on that same connection/thread. Never substitute
`thread_sensitive=False`, parallelize repository writes, or put network effects in
the callback. Storage assumes Django's default database; custom routers/multi-DB
transactions need a purpose-built driver. All models are scoped by tenant/storefront
and mode. Generic entity references deliberately have no cascading user deletion.
Handle GDPR retention/deletion explicitly through audited host administration.

Built-in reactions preserve signed snapshots and make no implicit API reads.
checkout.paid/order/subscription deliveries converge even when reordered. Only
subscription.started creates a missing local subscription; updates do not invent
one. Unknown events remain audited/dispatched. Optional refunds/chargebacks retain
full financial snapshots. Customer bindings are never an ownership fallback.
The alpha follows Fluent's last-delivery-wins snapshot semantics: dedup is not
event ordering; reconcile stale/conflicting events explicitly.

Outbox is durable, not an automatic sender. Implement a worker that claims rows
with database locks, sends using an idempotent consumer key (scope + outbox primary
key), and marks delivered_at after success. Delivery is at least once, not exactly
once across external systems. Do not delete an outbox row before successful delivery.
Local-created notifications can precede eventual ownership linkage; consumers must
read current persisted ownership and retry/defer unattributed resources, not infer
it from customerId. No entitlements or email side effects are enabled by default.

Admin pages are read-only, but signed envelopes may contain personal data. Grant
model view permissions only to trusted staff and apply your retention policy.
